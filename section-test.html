A partir de este punto, todo lo construido previamente se conserva como modelo mental, no como estado final del sistema. En Fase-0, el objetivo fue claro y acotado:
demostrar que es posible mover grandes volúmenes de datos de forma eficiente desde un archivo Parquet hacia un motor SQL, entendiendo I/O, tipos y performance.
Ese objetivo se cumplió con un script único, full-load.py, que ejecuta el flujo completo de principio a fin. Ahora, en Nivel-1 Fase-1, el objetivo cambia.
Cambio de objetivo

🧠 ¿Qué está cambiando realmente?

En esta fase no estamos aprendiendo nuevas librerías.
Estamos cambiando la forma en que el sistema vive y evoluciona.
Estado anterior
"un script que carga datos"
→
Estado objetivo
un sistema de ingestión con estado persistente y arquitectura explícita
Este cambio comienza antes de modularizar.
📍 Estado actual del proyecto

El proyecto hoy se apoya en un único script

Lee un archivo Parquet completo — itera por row_groups — normaliza tipos — usa COPY para cargar directamente a PostgreSQL — ejecuta todo el flujo en un solo proceso, de forma end-to-end.
Este enfoque es válido, eficiente y muy común en la industria. De hecho, muchas empresas se quedan aquí.
⚠️ Problema real del enfoque "script único"

Aunque funcional, tiene implicaciones cuando el sistema crece

Estado
Todo el estado vive en PostgreSQL — sin capa intermedia persistente
✕
Fallo
Si algo falla, se debe reiniciar todo el proceso
No hay versionado de datos, trazabilidad entre etapas, ni separación de responsabilidades. El script mezcla extracción, normalización, carga y decisiones de infraestructura en un solo lugar.
el sistema funciona, pero no evoluciona bien
🎯 Objetivo de esta etapa

Antes de modularizar

Antes de dividir el pipeline en múltiples módulos, vamos a dar un paso intermedio pero crítico:
incorporar MinIO como backend de almacenamiento, manteniendo un script único e integral.
Esto nos permite:
Lakehouse storage / cómputo separados capa Bronze persistente sin fragmentar el código
🪣 Primer cambio estructural

MinIO como primer cambio estructural

Antes
PostgreSQL como primer destino del pipeline
→
Ahora
MinIO como estado duradero del sistema
MinIO se convierte en la primera capa del Lakehouse (Bronze). PostgreSQL pasa a ser un consumidor posterior, no el origen del pipeline.
Bronze layer almacenamiento persistente PostgreSQL → consumidor
