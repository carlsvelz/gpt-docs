## ¿Cómo vamos a trabajar?

En lugar de seguir el típico tutorial tradicional, vamos a utilizar **TUTOR, nuestro Harness Learning Runtime**, que está integrado directamente con nuestra plataforma Developer Docs.

Ahora, ¿qué es TUTOR y cómo funciona?

Básicamente, TUTOR conecta los agentes de código con todo nuestro ecosistema de aprendizaje: Roadmaps, Developer Docs, laboratorios y proyectos.

Actualmente puedes utilizarlo desde tres agentes de código:

- Claude Code.
- OpenAI Codex.
- OpenCode.

¿Y esto qué significa? Pues que no vas a estar saltando entre una documentación por un lado y tu editor por otro. TUTOR conecta todo ese contexto directamente con tu agente de código.

Por ejemplo, mientras desarrollamos nuestro Data Warehouse, podrás consultar la documentación, entender los conceptos, explorar las instrucciones de cada laboratorio y ejecutar las actividades desde tu propio entorno de desarrollo.

Pero aquí viene una de las partes más interesantes: TUTOR no solamente conecta la documentación con tu agente, también permite validar tu progreso.

Es decir, tú desarrollas una actividad, ejecutas los pasos correspondientes y, cuando hayas terminado, confirmas la actividad para que TUTOR pueda validar los resultados.

De esta manera, no se trata simplemente de pedirle a la IA que escriba todo el código por ti. Se trata de aprender mientras trabajas con agentes de programación, siguiendo una ruta estructurada y comprobando que realmente estás consiguiendo los objetivos de cada laboratorio.

Así que vamos a dejar tanta explicación y pasemos a la práctica.

Primero vamos a configurar nuestro entorno, conectar TUTOR y preparar todo para comenzar con **Analytics Starter**.

Perfecto. Una vez que hayas instalado TUTOR y lo hayas conectado con tu agente de código, vas a encontrar algo bastante interesante: una integración llamada **MCP**, que expone dos componentes fundamentales de nuestra arquitectura: `tutor` y `tutor-memory`.

Ahora, espera un momento. ¿Qué es MCP y por qué nos interesa?

MCP significa **Model Context Protocol**. Es un protocolo que permite conectar los agentes de código con herramientas, recursos y servicios externos mediante una interfaz estandarizada.

¿Y por qué hacemos esto?

Porque no queremos que TUTOR dependa exclusivamente de Claude Code, Codex u OpenCode. Queremos que nuestro runtime pueda trabajar con diferentes agentes compatibles con MCP, sin tener que construir una integración completamente diferente para cada uno.

En otras palabras, MCP es el puente que conecta tu agente de código con las capacidades de TUTOR.

Pero vamos a lo interesante. Dentro de esta integración tenemos dos componentes.

El primero es `tutor`.

Este es el componente que permite que tu agente acceda a nuestro ecosistema de aprendizaje: Roadmaps, Developer Docs, laboratorios, instrucciones y proyectos.

Por ejemplo, cuando comencemos a desarrollar nuestro Data Warehouse, tu agente podrá consultar el contexto del proyecto, recuperar las instrucciones de cada actividad y trabajar siguiendo la estructura que hemos definido en Developer Docs.

Así que no tienes un agente trabajando a ciegas o inventándose los pasos del proyecto. Tiene acceso al contexto que necesita para desarrollar las actividades.

### 2. TUTOR Memory: continuidad entre sesiones

Y aquí viene una de las partes que más me gustan de esta arquitectura.

El segundo componente es `tutor-memory`.

Pensemos en algo: estás trabajando con Claude Code, desarrollas varias actividades, tomas decisiones técnicas, solucionas algunos errores y finalmente cierras la sesión.

Al día siguiente vuelves a abrir tu agente. ¿Qué sucede? El agente no conserva automáticamente todo el contexto de la sesión anterior.

Y aquí es donde entra TUTOR Memory.

Esta es nuestra capa de continuidad. Permite recuperar información relevante de sesiones anteriores: en qué laboratorio estabas trabajando, qué decisiones tomaste, qué problemas solucionaste y qué actividades quedaron pendientes.

Pero ojo, no estamos guardando absolutamente toda la conversación. La idea no es convertir la memoria en otro historial de chat.

Guardamos el contexto que realmente necesitas para continuar trabajando.

Además, esta memoria es local, privada y está aislada por proyecto.

Y hay otro detalle interesante: **la memoria puede viajar con tu repositorio.**

Por ejemplo, si necesitas continuar el proyecto desde otra máquina, puedes exportar la memoria mediante `tutor-memory export`. Esto genera un directorio `.tutor-memory/` con su manifest y los bloques de memoria comprimidos, que puedes versionar junto con el proyecto.

Posteriormente, en otra máquina, ejecutas `tutor-memory import` y recuperas esa continuidad.

Es decir, no dependes de que la memoria esté guardada en una conversación o en una plataforma externa. La continuidad está vinculada a tu propio proyecto.

Y algo importante: TUTOR Memory no reemplaza Developer Docs, tampoco representa el progreso oficial del roadmap. Cada componente tiene una responsabilidad diferente.

Developer Docs contiene el conocimiento estructurado. TUTOR conecta ese conocimiento con tu agente. Y TUTOR Memory permite recuperar el contexto necesario para continuar trabajando.

Así que quédate con esta idea:

----

Uno te permite acceder al conocimiento y las capacidades de nuestro ecosistema; el otro permite que tu agente retome el trabajo donde lo dejaste.

Y ahora sí, teniendo clara esta arquitectura, vamos a nuestro proyecto Analytics Starter y veamos cómo funciona todo esto en la práctica.
